# Architecture Docs & Diagrams

Architecture documentation shows *how the system fits together* — the structure ADRs decide and the domain records (`rules/domain.md`) name, made visual. It is **living**: every diagram must match the code at all times, and a structural change updates its diagram in the same change (see `rules/maintenance-invariant.md`).

Diagrams are authored in **Mermaid** so they live in version control as text, diff cleanly in PRs, and render in most viewers — no binary image drift.

## Where it lives (CLI-owned, ADR 0036)

Views are registry records in `docs/architecture/`, scaffolded and indexed by the CLI —
one file per concern, never a single mega-file:

```bash
living-docs write new view "Context" --kind context     # docs/architecture/context.md
living-docs write new view "Backends" --kind container
living-docs manage index view                            # regenerates architecture/index.md
```

`--kind` seeds the CLI-validated `kind:` frontmatter from the closed vocabulary `context |
container | component | flow | sequence | state | data-model | deployment`; the generated
`architecture/index.md` sorts rows in that C4/arc42 zoom order (kind rank, then filename),
so the index reads outside-in without hand-maintenance. The docs-handwrite hook covers
`architecture/` exactly like the numbered type directories: records are born via `write new
view`, the index via `living-docs manage index`, and only the body below the closing `---` is
hand-edited. Views carry no status and are never superseded — they are living documents
updated in place; git history is the trail.

The architecture index (`index.md`, OKF reserved listing, no frontmatter) is reachable from the bundle-root `docs/index.md`. Each view file is a standalone **OKF concept** (`type: Architecture View`): frontmatter, then a single `#` H1, then `##` sections. A legacy single `docs/architecture.md` is brought current by re-creating each of its diagrams as a view record.

## The standard views

Cover the views the system actually has — don't invent diagrams for their own sake. Common ones:

| `--kind` | View | Mermaid type | Answers |
|---|---|---|---|
| `context` | **Context / high-level** | `flowchart` / `graph` | What are the major components and how do they connect to the outside world? |
| `container` | **Containers** | `flowchart` | What deployable/runnable pieces exist and how do they talk? (C4 level 2) |
| `component` | **Module layout** | `flowchart` | How is the code organized into modules and what depends on what? |
| `flow` | **Process / data flow** | `flowchart` with direction | How does data move through a key operation (ingest, backfill, request)? |
| `sequence` | **Tool-calling / request flow** | `sequenceDiagram` | How does a request actually execute across actors over time? |
| `state` | **State** | `stateDiagram-v2` | What states does an entity move through? (lifecycles, retention) |
| `data-model` | **Data model** | `erDiagram` | What entities exist and how do they relate? (schema, FKs, cardinality) |
| `deployment` | **Deployment** | `flowchart` | Where does each container run and over what infrastructure? |

## Per-view instrument binding (which views are checked vs inspection)

"Living — must match code" is only real for a view that has an instrument keeping it honest; the rest rely on the no-drift discipline (inspection), which a constraint-without-an-instrument is a vibe. State, per view, how drift is caught — and prefer a deterministic check where one exists:

| View | Drift caught by | Kind |
|---|---|---|
| **Module layout** | a **dependency-conformance check** if your project has one (ArchUnit · dependency-cruiser · Deptrac · import-linter) on a committed ruleset | deterministic |
| **Data model** | a schema/migration diff or ORM-schema check, where one exists | partial |
| **Module / component** | **distill-from-code** where an oracle exists — generate the view from the dependency graph rather than hand-drawing it, so it cannot drift from the imports it depicts (recipe: *Generated views*) | deterministic where wired |
| **Process / sequence / state** | the no-drift maintenance rule (review/inspection) — no deterministic oracle, except a state diagram exported by a declarative state-machine library (recipe: *Generated views*) | inspection |

Where a deterministic oracle exists, **prefer distilling the view from code** over hand-drawing it; reserve inspection for the views that genuinely have no oracle (the judgement residue), and say so per view rather than asserting "must match code" uniformly. A structural conformance rule SHOULD link back to the **ADR** that motivated it (the rule's ADR is its provenance; the ADR's fitness function is its instrument — `rules/adr-conventions.md` rule 6).

## Generated views (stamped region + runner)

A view whose kind has a code oracle can have its diagram generated by the project's own extractor and kept fresh by a runner script and the project's CI. The `living-docs` binary runs no extractor (tool and judgment work runs outside it): it splices the extractor's output into the view and stamps it, and `check` compares the stamp.

The generated part of the view body sits between an opening marker and the line `<!-- end generated -->`:

```
<!-- generated by: <command> | inputs: <glob>[, <glob>...] | sha256: <hex> -->
```

`<command>` is the one-line extractor command, `<glob>` the repository-relative files the diagram depends on, and `<hex>` the SHA-256 of those files. The region holds the opening ` ```mermaid ` fence, the extractor's Mermaid text and the closing fence, so `check` sees a fenced diagram and never parses a marker as Mermaid. Everything outside the markers is hand-owned prose. The region is written only by the splice, never edited by hand: a fix goes into the extractor's configuration or the declared mapping, then the region is regenerated. The older marker `<!-- generated by: <command> -->` with no stamp stays valid; it is never checked for staleness and the runner reports it as skipped.

Write the region with `manage view`:

```bash
bash scripts/crate-graph.sh | living-docs manage view view/<name> --splice --inputs 'Cargo.toml' '*/Cargo.toml' --command 'bash scripts/crate-graph.sh'
```

Make the marker command a call to a reviewed project script (here `scripts/crate-graph.sh`, a `set -euo pipefail` script that prints the Mermaid), not an inline pipeline: the script is reviewed, tested and versioned like any other code, and the marker stays one short line.

`--splice` reads Mermaid from standard input, writes the region and the stamp, and writes no byte when the result is identical. A second run without `--command` keeps the recorded command. A glob that is absolute, holds `..`, or resolves outside the repository is refused, and so is one whose every match `.gitignore` excludes.

Keep it fresh with the runner `skills/living-docs/scripts/regen-views.sh [--check] [--docs-dir DIR]`: for each view under `architecture/` it runs the command of the marker from the repository root and splices the output; a command that fails, in any stage of a pipeline, makes the runner fail naming the view. With `--check` it runs the command inside a scratch copy of the repository, so neither the bundle nor the real tree changes, and exits 1 naming each view whose region would change; run that in the project's CI and in a local `check` target. A view file must be named as a view slug, since the splice finds the view by it. Set `LIVING_DOCS_BIN` when the binary is not on `PATH`; otherwise the runner uses the newer build under `target/`.

**The marker command is code.** The runner executes the marker text as shell, and a pull request can rewrite it. Review a marker change like a change to a script. Run the runner only where the pull request's own code may already run: never under `pull_request_target`, never in a job that holds secrets, and never on a self-hosted runner for an untrusted ref.

`living-docs check` adds a `stale-view` advisory, exit 0, when the hash of a stamped region's inputs no longer matches its stamp: a changed manifest shows up at commit, before CI. Stamp narrow inputs: a schema, migrations, a compose file, an OpenAPI document or manifests. An import-graph view over source files is flagged by the inputs hash on nearly every commit, so leave it to the runner's `--check` in CI and stamp only the manifests it depends on.

Only some kinds have a code oracle: `component` (module layout) from an import graph, and `data-model` from a schema. The kinds `context`, `container`, `sequence`, `state`, `flow` and `deployment` have no import-graph or schema oracle and stay hand-authored (inspection, as in the table above); where a declarative state-machine library is in use, it may export a `state` diagram the same way. Per-stack extractors named by research 0005:

| Stack or source | Extractor | Output |
|---|---|---|
| TypeScript / JavaScript | dependency-cruiser | Mermaid natively |
| PHP | deptrac | Mermaid natively (its formatters) |
| Rust | `cargo metadata --format-version 1 --no-deps` piped through `jq`, in a project script (this repository's `scripts/crate-graph.sh`, stamped into `architecture/crates.md`) | the script builds the `graph TD` |
| SQL schema | tbls | Mermaid ER diagram |
| State machine | a declarative state-machine library that exports Mermaid | Mermaid |

Sort node and edge order in what the command writes, so a rerun on unchanged code yields no diff. The command text must be one line and must not itself hold `-->`, `--!>`, `<!--`, `| inputs:` or `| sha256:`; a script it calls prints any arrow it likes.

Limits: the runner runs in the project's CI or on a developer's machine, never in `living-docs check` or the pre-commit hook, since both must not depend on an installed extractor. `check` validates the Mermaid and the stamp but cannot prove the diagram matches the code; the runner's `--check` does. As a rough heuristic, a graph over about 25 nodes is hard to read as drawn: group nodes into components by a declared path-to-component mapping before rendering, and keep automatic clustering out of the default path.

## Completeness checklist (arc42 / C4 / ISO-42010 as vocabulary, not a new index)

The bundle's *index* stays as defined above. Borrow the established frameworks only as a **completeness checklist + shared vocabulary** — not a competing layout: does the architecture cover context/scope, building-block (container/component) structure, runtime/dynamic behavior, deployment, cross-cutting concepts, the decision trail (ADRs), **quality requirements / NFRs** (the quality-attribute scenarios — see `rules/prd-conventions.md`), risks, and glossary? Use **C4** levels (context → container → component) as the zoom vocabulary for the structural views, and **ISO-42010**'s concern→view traceability as the discipline that every stakeholder concern is framed by at least one view. Adopt the names and the checklist; do not import arc42's 12-section template as a parallel index — the existing index, typed views, and ADRs already cover it. Provenance (instrumentalized, not invented): arc42 (STARKE; HRUSCHKA), C4 (BROWN), ISO/IEC/IEEE 42010, Views-and-Beyond (CLEMENTS et al., SEI).

## Tool-calling / sequence diagrams (when applicable)

When the system's behaviour is best understood as a *conversation between actors over time* — an MCP/tool call, an agent invoking tools, a client→server→DB round trip — use a `sequenceDiagram` to make the flow concrete. Show the actors as participants and each call/return as a message. This is the clearest way to evidence "how it actually works" for tool-driven or multi-actor systems.

```mermaid
sequenceDiagram
    participant Client
    participant Server as MCP Server
    participant DB as SQLite
    Client->>Server: tool call (args)
    Server->>DB: query / write
    DB-->>Server: rows / result
    Server-->>Client: structured result
```

Include a sequence diagram only where it earns its place — a tool surface, a lifecycle with ordering, a non-obvious multi-step flow. Skip it for trivially linear calls.

### Checking a lifecycle over time (TLA+)

A flat `kind: state` view (no composite states, no `--` regions) can be model-checked in the project's own CI. The binary only prints the module; it never runs a checker.

1. Generate the module in CI and never commit it: `living-docs manage view architecture/order-lifecycle --export tla > order_lifecycle.tla`. The module is named after the view slug with `-` as `_`, so the file name must match. The output is byte-stable for the same view.
2. Write the properties in a separate module that `EXTENDS` the generated one, with its own `.cfg` (`SPECIFICATION Spec`, then your `INVARIANT` and `PROPERTY` lines). The names `States`, `Terminal`, `Init`, `Next`, `TypeOK` and `Spec` are a stable contract. The per-transition action names (`T1`, `T2`, …) are not: they follow source order, so inserting a transition renumbers them. Write properties over `state`, never over an action name; each state is the string constant of its Mermaid id (`state = "paid"`), and `[*]` gives `Init` and, as a target, a terminal state.
3. Run TLC from a `tla2tools.jar` whose SHA-256 your CI pins and verifies before use, for example `java -cp tla2tools.jar tlc2.TLC -config Orders.cfg Orders`.

The model over-approximates: guards (a transition's label is kept only as a comment) and data are not modelled, so a property that depends on them is yours to encode.

## Rules

1. **Mermaid, in-repo, text.** No exported PNG/SVG that can silently drift from the code.
2. **No-drift.** A change to schema, data flow, module layout, or a component relationship updates the relevant diagram(s) in the *same* change. A structural PR with a stale diagram is incomplete.
3. **Use the domain records' vocabulary** (`docs/context/`, generated index). Name nodes and participants with the project's domain/module terms, not ad-hoc labels — diagrams and prose must agree.
4. **One view per diagram.** Don't cram the data model and the request flow into one graph. Split by concern; index each.
5. **Indexed.** Every view file is listed in the architecture index, which is listed in the top-level Docs index.

## Anti-patterns

- A diagram that contradicts the code — worse than no diagram, because it misleads with authority.
- Screenshot/exported-image diagrams that can't diff and rot immediately.
- A single mega-diagram trying to show everything at once.
- Diagrams added but never wired into the index (orphans).
