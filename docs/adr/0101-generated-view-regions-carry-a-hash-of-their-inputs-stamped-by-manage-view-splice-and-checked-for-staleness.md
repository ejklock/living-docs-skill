# 0101. Generated view regions carry a hash of their inputs, stamped by manage view --splice and checked for staleness

## Context

Architecture views ([ADR 0036](0036-architecture-views-are-a-registry-doc-type-on-a-named-identity-with-a-kind-sequenced-generated-index.md)) can carry a generated region between `<!-- generated by: <command> -->` and `<!-- end generated -->`, kept fresh by a regenerate-and-diff job each project writes in its own CI (skills/living-docs/rules/architecture-diagrams.md). Nothing in the bundle says when the code behind a generated diagram changed after the diagram was written, so a project without that job, or a commit before CI runs, keeps a stale diagram with `check` green. Issue 0144 kept the binary from reading the markers, and [ADR 0096](0096-check-advises-on-an-inline-code-repository-path-that-no-longer-exists.md) limits reads outside the bundle to existence. A design review on 2026-11-22 weighed an inputs hash, a CI-only runner and an in-binary graph snapshot; the owner chose the runner plus an in-binary splice and a staleness advisory.

## Decision

We will make a generated region carry the inputs it was generated from and a hash of them, written by the binary and recomputed by `check`.

- The opening marker becomes `<!-- generated by: <command> | inputs: <glob>[, <glob>...] | sha256: <hex> -->`. `<command>` stays text the binary never runs.
- `living-docs manage view <view> --splice --inputs <glob>...` reads Mermaid text from standard input, replaces the generated region of the view (creating it at the end of the body when absent), and stamps the inputs and their hash. The hash covers every file the globs match under the repository root that `.gitignore` does not exclude, in sorted repository-relative path order, each as its path and its content with line endings normalised to `\n`; a symlink is never followed and counts as its path and its target text, as git stores it.
- `check` recomputes the hash of every stamped region of an architecture view and, when it differs, reports a `stale-view` advisory naming the view, the region's line and the globs; a stamp it cannot check (malformed, or a glob it refuses) is reported under the same kind. A stamped region in any other record is not judged. Following [ADR 0095](0095-a-new-check-rule-starts-as-an-advisory-and-becomes-a-violation-only-by-a-later-adr-that-counts-it-over-real-bundles.md) it starts as an advisory.
- A runner script ships with the skill: it runs the command a marker names, pipes the output to `--splice`, and with `--check` fails when the region would change. It runs in a project's CI and on a developer's machine, never inside the binary.

This amends ADR 0096's rule that the binary never reads a file outside the bundle: `check` and `--splice` read the content of the files a stamped region declares, with the same guards (repository root only, no absolute path, no `..`, no symlink that leaves the root). It also reverses the issue 0144 choice that the binary never reads the markers.

## Consequences

- A stale generated diagram shows at commit, with no extractor installed and no CI job, for every view whose region is stamped.
- The hash covers inputs, not the extracted graph, so any byte change to an input flags the view even when the diagram would not change. The recipe therefore stamps narrow inputs (one schema, a migrations folder, a compose file, an OpenAPI file, workspace manifests) and leaves import-graph views to the runner's `--check` in CI.
- Two branches that change the inputs conflict on the stamp line; regenerating resolves it.
- The marker grammar becomes a public contract kept in consumer files: changing it later needs a migration through `manage fmt`.
- Hand-drawn kinds (context, sequence, flow) gain nothing here; `path-missing` and review stay their instruments.
- Fitness functions: `--splice` twice with the same input writes no byte; `check` reports `stale-view` after an input changes and not after only the view's prose changes; a glob reaching outside the repository root is refused.
