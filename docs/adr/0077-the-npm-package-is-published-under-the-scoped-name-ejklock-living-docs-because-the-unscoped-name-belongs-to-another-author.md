# 0077. The npm package is published under the scoped name @ejklock/living-docs because the unscoped name belongs to another author

## Context

[ADR 0067](/adr/0067-an-npm-package-wraps-the-released-binary-as-a-second-distribution-channel-so-npx-living-docs-resolves.md) decided to publish the released binary on npm as a thin wrapper under the name `living-docs`, recording the name as unclaimed on 2026-10-19. On 2026-10-21 another author (`vios94`, repository `Akiles94/living-docs`) published `living-docs@0.2.0` with its own `living-docs` bin (`npm view living-docs maintainers time.created`). Publishing this repository under that name now fails with 403, and the `publish-npm` job has been skipped on every release since because the `NPM_TOKEN` secret is absent. Issue #84 on GitHub asks for the channel and for the name decision.

## Decision

We will publish the npm package as `@ejklock/living-docs`, a public scoped package, through npm trusted publishing, and keep everything else ADR 0067 decided.

- **Name.** `npm/package.json` declares `"name": "@ejklock/living-docs"`; the `bin` entry stays `living-docs`, so `npm install -g @ejklock/living-docs` installs the same `living-docs` command.
- **Invocation.** The documented forms are `npm install -g @ejklock/living-docs` and `npx @ejklock/living-docs <verb>`.
- **Credential.** The `publish-npm` job authenticates with npm trusted publishing: GitHub Actions OIDC (`id-token: write`), npm CLI 11.5.1 or later and Node 22.14 or later, per https://docs.npmjs.com/trusted-publishers. No npm token is stored in the repository, and provenance is generated by the registry flow.
- **First publish.** npm configures a trusted publisher from the settings of an existing package, so the owner publishes the first version from a workstation with 2FA and then registers `ejklock/living-docs-skill` with workflow `release.yml` as its trusted publisher.
- **Staged release.** The job runs `npm stage publish`; the trusted publisher does not allow direct `npm publish`, so each version waits for the owner's 2FA approval (`npm stage approve <stage-id>` or the npmjs.com Staged Packages tab) before it goes live, per https://docs.npmjs.com/staged-publishing (npm CLI 11.15.0 or later).
- **No silent skip.** The job no longer skips when a secret is absent; a failed npm publish shows as a failed job.
- **Unchanged from ADR 0067.** Thin wrapper over the release asset, postinstall download with sha256 verification, lazy download in the shim, version lockstep with `VERSION`, and the job running after the release-asset verification.

Rejected alternatives:

- **Keep `living-docs`.** The name belongs to another author; claiming it depends on a third party and may never happen.
- **`@klock/living-docs`.** Requires creating an npm organization for a single package today; the scope can move to an organization later by deprecating the personal one.
- **`living-docs-cli` (unscoped).** A short `npx` form, but unscoped names can be squatted beside it and sit next to the unrelated `living-docs` package, which an agent guessing `npx living-docs` would confuse with this one.
- **Direct `npm publish` from CI.** Fully automatic, but npm's trusted publisher form marks it as not recommended: anyone able to run `release.yml` would publish a version with no human 2FA.
- **A granular token with 2FA bypass as the `NPM_TOKEN` secret.** Works with the workflow as it was, but stores a long-lived write credential that skips 2FA; npm's token page flags the option as a security risk for CI and points to trusted publishing.

## Consequences

**Easier / gained:**
- The channel can ship: the scope belongs to the owner, so no third party can take the name.
- No publish secret to store, rotate or leak.

**Harder / accepted trade-offs:**
- `npx living-docs` still resolves to the other author's package; the documentation must always name the scope, and an agent guessing the bare name gets the wrong tool.
- The package is tied to the owner's personal npm account.
- Every release needs one manual 2FA approval before the npm version goes live; until then `npx @ejklock/living-docs` resolves to the previous version.
- The first version is published by hand, outside the release workflow and without provenance.
- A release whose trusted publisher is missing or misconfigured fails the `publish-npm` job; npm does not validate the configuration when it is saved.

**Follow-ups:**
- The owner publishes the first version and configures the trusted publisher with direct publish disabled; the next release tag stages through the workflow and the owner approves it.

## Verification

**Implementation impact:** `npm/package.json`, `npm/README.md`, `README.md`, `scripts/tests/npm/run.sh`, `.github/workflows/release.yml`.

**Verification criteria:**
- `npm pack --dry-run` in `npm/` reports the package name `@ejklock/living-docs` and the bin `living-docs`.
- No surface in the repository teaches `npx living-docs` or `npm install -g living-docs` without the scope.
- `release.yml` references no `NPM_TOKEN`; `publish-npm` has `id-token: write` and stages with `npm stage publish` on npm 11.15.0 or later.
- `make check` passes, including `scripts/tests/npm/run.sh`.
- After the first release tag following the trusted publisher setup, `npm view @ejklock/living-docs version` equals `VERSION` and the version shows a provenance attestation.
